# One real challenge with prediction-market data is determining whether two contracts are truly the same

I made a tool that matches Polymarket and Kalshi contracts by their titles, then I reviewed the
results myself. I manually checked the published rule text for 30 of these pairs to see how many
were true matches.

Three were.

Three out of 30 doesn't really mean a 10% match rate. The sample is too small to pin the number
down that precisely. What stands out is the pattern of failures.

That part was clear: the mismatches were mechanical, and nearly all of them could be traced back
to the **published rule text**. These weren't close calls from fuzzy matching. They were
structurally different contracts that happened to share vocabulary.

Different weather stations using the same city name. Cumulative thresholds on one venue versus
exclusive buckets on the other. Event windows with different boundaries. Retirements compared to
announcements of retirement. Race markets versus standalone markets. One pair had complementary
framings, so the hedge direction was reversed. And a few cases where Kalshi published rule
templates that still had placeholders in them. That last one is the category the rule text can't
explain, because there wasn't any.

That is the data problem. Pulling the API is easy. Knowing what the contract actually *means* is
what makes naive cross-venue analysis fall apart.

## What's included in this repo, and what's not

All the read-only measurement code is here:

- universe enumeration for both venues
- both fee models
- the IDF-weighted candidate matcher
- the Gamma keyset durability probe
- the intra-PM complement scanner
- the hedge walker
- unit tests over the arithmetic

The adjudication labels are not included. Those 30 hand-read verdicts and the resolution-text
sample behind them are the actual work product and remain unpublished, so `walk_hedge.py` runs
using a verdicts file that you provide. `text_verdicts.example.json` shows the schema it expects.

Nothing here places orders, holds keys, or touches any accounts. Every script is a
public-endpoint GET request.

## How to reproduce

Python 3.10+. No dependencies outside the standard library; `pytest` only for the tests.

```bash
python3 -m pytest tests/ -q          # 19 tests, no network

python3 probe_pm_keyset.py           # Gamma keyset walk, capped
python3 probe_pm_keyset.py --uncapped

python3 probe_overlap.py --refresh   # enumerate both venues, cache a snapshot (~6 min)
python3 probe_overlap.py --show 20 --min-score 0.5   # report from cache, no network refresh

python3 scan_pm_complements.py --limit 1000 --contracts 100
python3 walk_hedge.py --notional 100 # needs your own verdicts file
```

If a snapshot is missing, it refreshes automatically, so the first run takes about six minutes
whether or not you use `--refresh`. Later runs read from the cache and skip the network walk, but
they still recompute the local candidate match, which can take some time on a full snapshot.

Your counts may not match the table below. The universe changes, and that snapshot is from before
a pagination change.

## What I measured

Read-only snapshot of both venues, filtered down to plausible non-sports binary matches with
two-sided books, then candidate pairs generated by IDF-weighted title overlap.

These counts come from one snapshot on 2026-08-16, produced by the **pre-keyset date-bisection
walk**, with `closed=false` and an end-date window running from 30 days before the snapshot to
900 days after it. Point-in-time, not standing current-universe totals.

| Polymarket live/not-closed markets in snapshot | 195,860 |

The enumerator uses Gamma keyset pagination now, on the same default horizon. The legacy offset
endpoint still dies at offset 2100, but keyset is the current path and the raw `closed=false`
walk terminates cleanly.

Generating pairs was never the interesting question. The interesting one is how many of those
pairs actually settle the same way.

So I picked 30 candidates *before reading any of them*: ten from the low band, ten from the
middle, and ten from the high band, and checked each one by hand against the full published
resolution text on both venues.

**Three out of 30 were actually the same contract.**

All three came from the middle band. The high band, which was supposed to be the easy part,
produced nothing. Higher title similarity didn't help the matcher in this sample. It just
concentrated the cases where two titles look alike because the instruments share a template, but
the settlement terms do not.

## Where it breaks

### Weather: same city, different station

Weather seemed like one of the biggest overlap classes at first. It failed across the board.

Kalshi and Polymarket will both describe the same city while resolving against different
stations, or even different source products. From the adjudicated sample and the wider candidate
review: Chicago Midway against O'Hare, Dallas DFW against Love Field, Denver International
against Buckley AFB, Houston Bush against Hobby, New York Central Park against LaGuardia.

Those stations can differ by more than the width of the bucket being traded. The title-level
match still calls them equivalent, even though the rules clearly say otherwise.

### Economic releases: cumulative threshold against exclusive bucket

One venue asks a cumulative threshold question, the other asks an exclusive bucket question.
"At least 58" still resolves Yes at 59.0. "Between 58.0 and 58.9" does not.

Economic releases, GDP and PPI ladders, launch-count markets, anything with buckets. You can
sometimes rebuild a cumulative contract by adding up the bucket contracts, but then you are
dealing with more legs, more fees, more spread, and more execution risk.

### Window seams

Small timing details can change the settlement. One venue asks whether something happens *after
issuance*; another asks whether it happens between January 1 and December 31. An event that
happens before issuance but within the calendar year splits the two contracts apart. You can't
see this from the title, but it's obvious once you read a couple paragraphs into the rules.

### Two short ones: event vs announcement, race vs standalone

"Retires by date X" is not the same as "announces retirement by date Y." The economic exposure
can look similar, but the contract still isn't the same.

"Will person X leave office before 2027?" is not the same as "Will person X be the next cabinet
member to leave?" The second question depends on what other people do.

### Complementary framings

This pair bothered me the most, because it's not a mismatch. It's a sign error. Kalshi asked an
"at least 6" type of question, while Polymarket asked a "5 or fewer" type. Those are complements,
so a Yes on Kalshi was the same as a No on Polymarket.

Any scanner that assumes a matched pair should hedge Yes on one venue against No on the other
gets the direction wrong here. It doubles the exposure and reports a flat book while doing so.

### Placeholder rule text

Some Kalshi markets publish rule templates with placeholders left blank. The contract is probably
normal internally, but when the public rule text just says `above || Count || by || Date || at ||
Time ||`, there's nothing an external matcher can do except fail closed.

### Embeddings don't fix this, and here's a documented case

An obvious objection to everything above is that IDF-weighted title overlap is a crude matcher, and
that a semantic model would not make these mistakes. I checked what the commercial feeds actually
do, because if the problem were solved I would rather find that out now.

Five vendors sell normalized cross-venue prediction-market data: PMXT, Dome, Adjacent News,
PolyRouter, and Probalytics. Of those, one ships general relation classification. PMXT's SDK
defines a closed `MatchRelation` literal of identity, complement, subset, superset, overlap and
disjoint, with a `confidence` float and a `reasoning` string alongside it. Dome and PolyRouter
solve matching for sports and only sports. PolyRouter and Probalytics otherwise do schema
unification, which is making the fields line up rather than deciding whether two contracts ask the
same question. None of the five publishes an accuracy figure.

Adjacent News is the instructive one, because its documentation shows the failure directly. Their
similar-markets endpoint ranks on cosine similarity over embeddings, not string overlap. The sample
response in their published API docs answers one query with two Kalshi contracts: New York winning
the 2026 basketball finals at `similarity: 0.91`, and Boston winning the same finals at `0.88`.

Those two contracts are mutually exclusive. Both cannot resolve Yes. They score as near-identical
because they are the same instrument template with one field changed, which is exactly what an
embedding is built to notice and exactly the wrong thing to notice here.

That is a documentation example rather than a measured error rate, and I have not run their API, so
I'm not presenting it as their accuracy. It is worth showing anyway, because it is what the vendor
chose as the illustration of the feature behaving correctly, and it reproduces the same inversion
that took out all ten of my high-similarity pairs. The endpoint also exposes a configurable cosine
floor whose own documentation notes it "is calibrated to the embedding model in use and is not
comparable across models," which is an honest statement that the threshold is a tuning parameter
rather than a correctness boundary.

So the point is not that nobody built cross-venue matching. Several people did, and at least one
built it carefully. The point is that a similarity score and a relation label are different
claims, and only the second one can be checked against the rules.

### And one that survives a perfect match: who certifies the outcome

Every failure above is a reason two contracts are not the same question. There's one more that
applies even when they are: the two venues don't settle the same way.

Kalshi settles through a regulated exchange. Polymarket settles through UMA's optimistic oracle,
where a bonded proposer asserts the outcome and a token-weighted vote decides anything disputed.
Wang (2026) reads prices inside that dispute window and finds the vote overturns the audited
rule-correct winner in 3.4% of disputed markets on hand verification, with Polymarket logging
over 1,150 disputed markets in the first half of 2026.

That rate is conditional on a dispute, so it isn't a haircut on every position. But disputes
arise where the rule text is ambiguous, and ambiguous rule text is exactly the population a
cross-venue matcher is already swimming in. A pair can pass adjudication on the text and still
diverge on who certifies it.

## Fees

Both venues now run taker-fee schedules shaped around `P * (1 - P)`, so the fee peaks near 50/50,
which is exactly where the two-sided depth usually lives.

Running the three adjudicated matches live, one direction was positive: about $0.57 on roughly
$98 of parked capital, held until 31 December 2026. That's about 0.6% over four and a half months
before any capital logistics, or about 1.6% annualized, which is below a risk-free baseline of 4
to 4.5%. Plus, that capital sits on two venues you can't quickly rebalance against each other.

That result isn't novel, and I don't want to present it as though it were. Gebele and Matthes
(2026) formalize the mechanism: when collateral stays locked until settlement, a near-certain
dollar is a delayed dollar, so prices carry a maturity-dependent settlement discount that they
recover as an annualized settlement wedge. The number above is one hand-walked instance of their
term structure, measured across two venues rather than one.

So the problem was never a lack of matches. It's that the matches that survive adjudication are
long-dated, tie up capital, and are limited by fees.

## What a usable data layer has to track

Most cross-venue work treats the venue API as the source of truth and uses the title as the join
key, or an embedding of the title, which is the same key with better manners. That's not enough.
At a minimum, you need:

- venue-specific pagination and universe boundaries
- fee schedules by market or series
- token and outcome polarity
- full resolution text
- settlement source, including station IDs
- window start and end semantics
- bucket against cumulative structure
- complementary framings
- historical cutoff boundaries
- settlement mechanism and dispute state (on Polymarket, Gamma's `umaResolutionStatuses`)

If you skip those, you end up with a dataset that looks clean but produces false arbitrage, false
overlap, and hedges that point the wrong way.

I'm thinking about packaging the audited layer behind this work: cross-venue match verdicts with
the reason attached, resolution-text fingerprints, fee schedules, source and station diagnostics,

## Appendix: API traps found during the measurement

It's not the main point, but this is why I don't trust a simple venue pull.

- Kalshi `/markets` and `/events` paginate with `cursor`, but `/incentive_programs` uses
  `next_cursor`.
- Kalshi `/markets?status=open` is dominated by generated Exotics/KXMVE combination markets.
  `/events?status=open&with_nested_markets=true` is the cleaner universe for this task.
- Kalshi silently ignores `category=` on `/markets`. Category has to be joined from series
  metadata.
- Kalshi historical data is split onto `/historical/*` behind a server-reported cutoff.
- Polymarket legacy Gamma offset pagination still fails at offset 2100. Keyset pagination is the
  current viable path.
- Polymarket prices have to come from CLOB order books, not stale Gamma marks, any time the price
  actually matters.

None of that is a complaint about API design. The point is that a plausible, non-empty response
can still give you the wrong dataset.
